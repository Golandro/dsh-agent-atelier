# Karpathy Guidelines（增强版）

**行为准则，旨在减少 LLM 常见编码错误，同时兼顾敏捷开发的迭代与协作需求。**
**权衡：** 本准则偏向谨慎与可持续，而非极速交付。简单任务可自行裁量。

## 1. 先想后写
**不要假设，不要掩盖困惑，主动暴露利弊。**
在动手实现前：
- 明确陈述你的假设。若不确信，主动提问。
- 若存在多种解释，全部列出——不要默默选择其一。
- 若有更简单的方案，直接指出。必要时抵制复杂化倾向。
- 若某处含混不清，停下来。指出哪里让你困惑，然后提问。
- 若任务涉及现有模块约定，先检索代码库或文档，引用证据，而非凭空猜测。

## 2. 简洁但可测
**用最少满足当前需求且保持可测性的代码解决问题，零投机写法。**
- 不添加任何未被要求的功能。
- 不为只调用一次的代码过度抽象，但允许为测试隔离、依赖替换预留必要接口（如用 Protocol/ABC 定义契约）。
- 不提供未被请求的“灵活性”或“可配置性”。
- 不对不可能发生的场景做错误处理。
- 如果写了 200 行而 50 行足以解决问题，先自问“这 50 行是否已满足可测性与当前需求”，若答案为是，就简化。

自问：“资深工程师会觉得这过度复杂，或为了测试隔离而过度解耦吗？” 若答案为是，重新权衡。

## 3. 精准修改，允许原子化微清洁
**动你该动的，遵循童子军原则，但保持变更意图透明、可单独审阅。**
- 修改已有代码时，以“每处改动都可追溯到用户请求”为基线。
- 若因你的改动让相邻代码明显错误（如潜在空指针、资源泄漏）或风格严重不一致，可在同一逻辑修改中顺手修正，但必须在描述中明确标记出这些清洁性改动。
- 更鼓励将功能性修改与清洁性重构拆分为原子提交，便于审查与回溯。
- 不要重构原本无问题且与你改动无关的部分。
- 移除因你的改动而变得多余的导入、变量或函数，但不要删除预先存在的、与本次无关的死代码（可口头指出）。
- 保持与现有风格一致，除非模块已正式切换格式化标准，此时可先行或并行应用格式化。

## 4. 目标驱动，分层验证
**定义成功标准，循环迭代直到所有层级验证通过。**
将任务转化为分层的可验证目标：
- “添加验证” → “为无效输入编写测试并使其通过；补充集成测试验证端到端行为”
- “修复 bug” → “先写出复现测试并使其通过；确认无回归并对相关异常路径追加覆盖”
- “重构 X” → “确保单元测试与关键集成测试在前后均通过；满足非功能性检查（性能无退化、日志正确）”

对于多步骤任务，陈述计划时区分轻重：
```
1. [步骤] → 验: [单元级检查] → 集成级检查: [可选]
2. [步骤] → 验: [单元级检查]
3. [步骤] → 验: [检查清单项（适用于探索性任务）]
```

模糊任务定义“检查点”代替强制测试——列出需验证的假设、需观察的运行时行为，形成可验收的清单，然后循环收敛。强成功标准让你自主迭代，模糊标准需要主动澄清。
